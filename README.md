# TOBD

## Инструкция для AI-агента: очистка лабораторных работ проекта

Инструкция выведена из анализа коммита `cleaned 2_1` (изменения файла `done/lab2_1.ipynb`
между двумя последними коммитами репозитория). Применяется ко всем остальным ноутбукам
проекта (`done/lab2_2.ipynb`, `done/lab2_3.ipynb`, `done/lab2_4.ipynb`, `done/lab_2_5/`,
`done/lab3_1/` и т.д.). Инструкция описывает общие принципы; конкретные решения по каждой
работе агент принимает сам, проверяя файл перед правкой.

---

### 0. Два раздела работы — два разных режима правки

Каждая лабораторная работа состоит из двух разделов, и правила очистки для них **разные**.
Перед правкой определи границы разделов: в ноутбуках они размечены заголовками
(`## Самостоятельная работа`, а часть по методичке идёт до этого заголовка; также ориентиры —
ссылки на рисунки/номера формул методички в markdown и комментариях `# ... (в методичке отсутствует)`,
`# ... по методичке` в коде). Если разметки нет — найди границу сам по наличию эталонных
рисунков/таблиц методички рядом с кодом и вынеси явный заголовок раздела.

**Часть 1. Работа по методичке (повторение примера с эталонным результатом).**
Код здесь **не трогать вообще**: ни сокращения, ни рефакторинга, ни замены функций, ни
переноса строк. Код повторяет методичку шаг за шагом, и именно это позволяет сверять результат
с её рисунками и таблицами; любое изменение кода ломает сопоставимость и делает сверку ложью.
Разрешены только: (а) правки markdown-пояснений вокруг кода, (б) очистка outputs от шума и
дампов при перезапуске, если сами ячейки не менялись, (в) добавление минимального комментария
там, где расхождение результата с методичкой требует объяснения. Существующие пояснительные
комментарии к строкам кода не удалять.

**Часть 2. Самостоятельная работа (собственное исследование).**
Здесь код **сокращать и переписывать можно и нужно**, потому что эталона для сверки нет и
читатель оценивает логику, а не совпадение строк с источником. Условия:
- кратко: минимум ячеек и строк, достаточный для доказательства вывода;
- всё обосновано: каждый выброс/обобщение кода сопровождается текстом «что делалось раньше →
  почему теперь так» там, где это не очевидно из контекста;
- предсказуемый результат: фиксировать `random_state`/seed, размеры разбиений, версии и порядок
  данных — чтобы повторный запуск давал те же числа, на которые ссылается текст;
- без избытков: если что-то непонятно или результат контринтуитивен — добавить короткое
  объяснение/анализ прямо в этот раздел, но ровно столько, сколько снимает вопрос, без
  разрастания в лекцию.

Дальнейшие пункты 1–8 применяются к обоим разделам, кроме явно оговорённых ограничений на код
из этого пункта (см. также п. 5).

### 1. Цель очистки

Превратить «черновой» ноутбук (расшифровка диалога с AI / конспект лекции) в **защитную
работу**: краткую, понятную, готовую к устной защите перед преподавателем, который знаком
с материалом методички.

Критерий качества каждого изменения — не «стало короче», а **«читатель без потери смысла
понимает, что сделано, зачем и почему именно так»**. Если сокращение уничтожает обоснование
решения или доказательство корректности — такое сокращение запрещено.

### 2. Что удалять и сокращать

**Теория и базовые понятия.** Не пересказывать то, что есть в методичке: определения
методов, формулы, историю вопроса, пошаговые объяснения стандартных функций
(«что такое k-means», «как работает pandas.read_csv»). Читающий знаком с материалом —
достаточно названия метода/функции в контексте задачи.

**Учебные примеры «на игрушечных числах».** В `lab2_1` был удалён отдельный cell с
демонстрацией MSE на вручную придуманных числах: он объяснял формулу, а не решал задачу.
Такие cell'ы удаляются, если они не несут результата по данным работы.

**Дублирующие сверки с эталоном.** Из `lab2_1` удалена функция `compare_with_book` и её
HTML-таблицы вида «все значения совпадают». Сверка с рисунками/таблицами методички нужна
как проверка, но не как отчёт: результат оформляется одной строкой вывода или комментарием
(«совпадает с рис. 4.2») рядом с основным результатом, а не отдельной таблицей на каждую
метрику.

**Шум в outputs.** Удалять: предупреждения библиотек (FutureWarning и т.п.), промежуточные
print'ы отладки, дампы датафреймов целиком, пустые outputs, артефакты форматирования
(линии `====`, рамки, HTML-обёртки от compare-функций). Сохранять/перезапускать так,
чтобы в notebook остались только outputs-доказательства (см. п. 4).

**Мета-текст диалога с AI.** Фразы вроде «Now let's...», «As I mentioned earlier»,
«Great question», пояснения самому себе про процесс редактирования — переписываются в
нейтральный технический текст или удаляются.

### 3. Что объяснять в комментариях (markdown и код)

Каждое содержательное действие сопровождается коротким текстом, отвечающим на один из
вопросов:

1. **Что выполняется и зачем** — одна-две строки перед логическим блоком
   («Нормирую признаки, т.к. KNN чувствителен к масштабу»).
2. **Какое решение принято при реализации** — выбор метода, параметра, порога, признака.
3. **Почему выбрано именно это** — причина в терминах данных или задачи
   («взял силуэт, а не elbow: кластеров мало, излом нечитаем»).
4. **Расхождения с методичкой** — если отступили, обязательно указать факт отступления
   и обоснование. Это не дефект, а защитный аргумент; молча отступать нельзя.

Формат: тезис + причина. Без вводных абзацев, без повторения того, что видно из кода.
Комментарии в коде — только там, где код не самоочевиден (нетривиальный параметр,
неочевидный срез данных); строчка `df.head()` комментария не требует.

### 4. Outputs как доказательства, а не декорации

Правило: **output остаётся в файле, если он подтверждает вывод работы** — график
результата, финальная таблица метрик, фрагмент данных, на котором строится утверждение.

- Выводы в markdown должны быть прослеживаемы до конкретного output выше по cell'ам.
- Большой таблицей показывать только нужное: в `lab2_1` полная таблица сравнения заменена
  указанием на совпадение; если таблица необходима — комментируются только те её части,
  которые требуют пояснения (аномальные строки, выбранный вариант).
- Большие таблицы нежелательны по умолчанию: чаще достаточно одной цифры/строки вывода.
- Графики, на которые нет ссылки в тексте работы, — удалить либо добавить ссылку.

### 5. Правила по коду

Применяются к разделу «Самостоятельная работа» (п. 0, часть 2). Код раздела «по методичке»
(п. 0, часть 1) не правится ни при каких условиях ниже — там допустима только очистка markdown
и outputs.

- **Не сокращать код ради сокращения.** В `lab2_1` код почти не изменился по объёму
  (11.4k → 10.3k символов) против markdown (12.5k → 5.5k): чистится текст, а логика
  анализа остаётся полной.
- **Заменять самописную реализацию стандартной функцией**, если цель была учебной, а
  результат тот же (в `lab2_1` ручная формула расстояния Кука заменена на
  `model.get_influence()`). Но если ручная реализация сама является предметом задания —
  оставить.
- **Обобщать повторяющиеся куски в функции/циклы.** В `lab2_1` проверка выбросов для
  нескольких Y свёрнута в общие `analyze_outliers` / `compare_without_row`. Важно:
  обобщение должно **повышать покрытие** (проверка применяется ко всем объектам сразу),
  а не срезать проверки. Сокращение числа вызовов за счёт отказа от проверок — запрещено.
- Cell'ы выстраивать в линейный сюжет работы: данные → подготовка → модель/анализ →
  выводы. Промежуточные эксперименты, не вошедшие в выводы, удалять вместе с их outputs.
- После правок ноутбук должен выполняться от начала до конца без ошибок; итоговые outputs
  — актуальные (получены перезапуском, а не остались от старой версии кода).

### 6. Пошаговый процесс для каждого файла

1. Прочитать весь notebook (код + markdown + outputs), найти границы разделов «по методичке»
   и «Самостоятельная работа» (п. 0) и зафиксировать, какой режим правки к каким ячейкам
   применяется; затем составить карту: какие выводы содержит работа и какими outputs они
   подкреплены.
2. Пройти markdown обоих разделов: вырезать теорию и мета-текст, переписать пояснения в формате
   «что/зачем/почему», проверить наличие раздела/строк о расхождениях с методичкой.
3. Пройти код раздела «Самостоятельная работа»: найти дубли и самописные аналоги стандартных
   библиотечных функций, обобщить циклы, обеспечить воспроизводимость (seed); ничего не удалять
   из логики анализа без явной причины. Код раздела «по методичке» пропустить целиком.
4. Пройти outputs: удалить шум и дампы, оставить доказательства, при необходимости перезапустить
   ячейки (перезапуск допустим и для части по методичке — при неизменном коде).
5. Финальная проверка связности: каждый вывод текста опирается на видимый output; каждый
   оставшийся output на что-то ссылается; код воспроизводится целиком, а часть по методичке
   побайтно совпадает с собой до правок (проверить `git diff` по code cells этого раздела).
6. Закоммитить с описанием в стиле истории репозитория (`cleaned <номер>`), отдельно от
   изменений других файлов.

### 7. Явные запреты

- **Не изменять код ячеек раздела «работа по методичке»** — ни сокращений, ни рефакторинга,
  ни замены библиотечных вызовов; этот раздел сверяется с эталоном, и правка кода делает
  сверку недействительной (п. 0).
- Не удалять элементы **только ради уменьшения объёма** — каждое удаление должно
  сохранять смысл и обоснованность работы.
- Не трогать содержимое и оформление других работ, кроме обрабатываемой; не делать
  выводов о них по их текущему состоянию.
- Не менять выводы работы и фактические результаты анализа — очистка касается формы,
  полноты обоснований и шума, но не чисел.
- Не оставлять в файле следы автогенерации (стиль переписки с LLM, разметку ботов).
